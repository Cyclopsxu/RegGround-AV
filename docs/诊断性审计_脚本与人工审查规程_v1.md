# 诊断性审计 · 脚本需求与人工审查规程 v1

**对象**:首轮全量结果 `logs/eval_set_v1_full_v3_5.jsonl`(commit `03c4701`)暴露的 246 个不可评分场景 + 907 个 uncertain 候选 + scene-0286 illegal-chosen。
**定位**:工程分诊,不产出 gold label,不进指标计算。审计者可查看全部信息(系统输出、benchmark 标签、sidecar)。
**产出**:三张交叉表、一份抽样审计工作表、一份逐场景处置表、一页诊断报告。
**时间盒**:脚本 0.5–1 天,人工审查 1.5–2 天,报告 0.5 天。

---

# 第一部分 脚本需求(`scripts/diagnostic_audit/`)

脚本分三个子命令,建议单文件 CLI:`python -m scripts.diagnostic_audit {crosstab|sample|render} ...`。全程只读输入,输出写入独立目录 `diagnostics/v1/`,不触碰冻结结果。

## 输入

| 输入 | 内容 | 来源 |
|---|---|---|
| `eval_set_v1_full_v3_5.jsonl` | 每场景一条:AuditLabel(verdicts、preference_ranking、chosen、stage_diagnostics、decided_by)+ 评分器结论(scorable / 不可评分原因) | 冻结结果 |
| benchmark labels | 每候选:anonymous_id ↔ variant_type、expected_verdict、difficulty、gt_precheck_status | Layer 1 输出 |
| ParsedSceneBundle 或等价缓存 | SceneFacts、narrative、trajectory_features、SceneQuery | 重放 parse 或读缓存 |
| RuleSubgraph 日志(如有) | matched_conditions、retrieval_mode、overrides_applied | Layer 2 telemetry |

> join 键:`(scene_id, frame_token, anonymous_id)`。脚本启动时必须校验 join 完整性:eval 侧每个候选都能在 benchmark 侧找到映射,否则报错退出——join 缺口本身就是一个发现。

## 子命令 1:`crosstab` — 交叉表与总量核对

输出 `diagnostics/v1/crosstabs.md`(人读)+ `crosstabs.json`(机读),内容:

**核对表(必须先对账)**

- 场景总数 = 259;不可评分 = 246 且三桶之和对得上(120 无可选 + 95 exclude + 31 hard_case);uncertain 候选总数 = 907。任何对不上的数字停下来先查评分器口径。

**交叉表(候选粒度)**

| 表 | 行 × 列 | 回答的问题 |
|---|---|---|
| T1 | uncertain × scenario_type | uncertain 是否集中在 UNKNOWN / 相位缺失场景 |
| T2 | uncertain × variant_type | 哪类合成变体最容易被判 uncertain(hard_case 高属预期,GT/conservative 高属异常)|
| T3 | uncertain × decided_by | uncertain 是规则引擎给的还是 LLM 兜底给的 |
| T4 | verdict(3 类)× scenario_type × difficulty | 全景分布,supplementary |

**交叉表(场景粒度)**

| 表 | 行 × 列 | 回答的问题 |
|---|---|---|
| T5 | 不可评分原因(3 桶)× scenario_type | 哪类场景贡献了不可评分 |
| T6 | no-choosable 场景的候选构成 | 每个无可选场景:vetoed/uncertain/cleared 计数向量的分布(如「6 全 uncertain」「3 vetoed + 3 uncertain」各多少)|
| T7 | exclude-chosen × gt_precheck 失败原因 | precheck 哪条谓词踢掉了这些 GT |

**派生指标**

- uncertain 率 = 907 / 总候选数,并按 T1–T3 各维度给分组率;
- `traffic_light_status_source == "none"` 的场景占比(相位缺失覆盖率,对应 SRS 已知风险点);
- 每张表附一行自动生成的「最大占比组合」提示,如 `T1: UNKNOWN 占 uncertain 的 xx%`。

## 子命令 2:`sample` — 分层抽样与工作表生成

**抽样规则**(seed=42,SHA-256 排序,与盲标包同法,保证可复现):

| 桶 | 抽样量 | 分层依据 | 强制纳入 |
|---|---|---|---|
| B1 no-choosable(120) | 24 | scenario_type 比例分层,每层 ≥2 | T6 中候选构成最极端的 2 个(如全 uncertain、全 vetoed)|
| B2 exclude-chosen(95) | 20 | gt_precheck 失败原因分层 | 每种失败原因 ≥3 |
| B3 uncertain 候选(907) | 30 | decided_by × scenario_type 双分层 | LLM-uncertain 与 rule_engine-uncertain 各 ≥10 |
| B4 hard_case-chosen(31) | 0(不抽) | — | 仅输出变体分布统计,人工不逐个审 |
| B5 特殊案例 | 1 | — | scene-0286 全量信息 |

> B3 与 B1 允许重叠(no-choosable 场景里的 uncertain 候选可能被两桶同时抽中),重叠时合并为一条审计项、双桶标记,避免重复看。

**输出** `diagnostics/v1/audit_worksheet.xlsx`(或 md/html),每行一个审计项,列分两区:

*证据区(脚本填好)*:
`audit_item_id` | `bucket` | `scene_id` | `frame_token` | `anonymous_id`(B3/B5)| `scenario_type` | `scene_facts`(展平为中文键值,同盲标包格式)| `narrative` | `retrieved_rules + overrides` | `trajectory_summary`(B3:仅该候选;B1/B2:该场景全部候选)| `system_verdicts`(全部候选的 status + decided_by + reason)| `chosen` | `benchmark 侧`(variant_type、expected_verdict、difficulty、precheck 状态)| `不可评分原因`

*裁定区(人工填)*:
`disposition_code` | `evidence_note`(一句话)| `benchmark_v2_action`(可空)| `needs_blind_confirmation`(bool)| `time_spent_min`(可选)

> 与盲标包的关键区别:证据区**刻意包含**系统结论与 benchmark 标签——诊断审计就是要对着答案找根因,不需要盲。

## 子命令 3:`render` — 可选的轨迹可视化

若盲标包配套的可视化工具已存在则直接复用;否则最小实现:matplotlib 把场景全部候选 waypoints + Map Expansion 的 stop_line / ped_crossing 多边形画在局部坐标系,每候选一色,标注匿名 ID,输出 `diagnostics/v1/figs/{scene_id}.png`,工作表中放相对路径。B1/B2 桶(需要比较多条候选)强烈建议有图;B3 可选。

## 脚本验收

- [ ] 只读输入、独立输出目录,重复运行结果逐字节一致(seed 固定);
- [ ] join 完整性校验通过或明确报告缺口;
- [ ] 核对表数字与首轮汇报数字一致(259/246/120/95/31/907);
- [ ] scene-0286 强制在册;
- [ ] 工作表 disposition_code 列带下拉校验(六码 + 挂起码,见下)。

# 第二部分 人工审查规程

## 处置码(每个审计项必填其一)

| 码 | 含义 | 流向 |
|---|---|---|
| `BENCH-FIX` | benchmark 标签/口径错(override 未后置、precheck 过严、exclude 语义问题)| benchmark v2 修订清单 |
| `FACT-FIX` | Layer 1 事实提取错(相位误读、行人误判、朝向夹角错)| Layer 1 bug 清单 |
| `FEAT-GAP` | 特征摘要缺少判定所需信息,弃权诚实但可通过扩充特征解决 | 特征扩充清单 |
| `JUDGE-MISS` | 信息充分但判定错/不敢判(prompt、规则引擎阈值)| 判定层调优清单 |
| `CORRECT-ABSTAIN` | 场景本身不可判,系统弃权正确,数据固有限制 | 计入"合理不可评分",不修 |
| `SCOPE-CUT` | 该细分样本量/质量低于 W1 阈值,应从 MVP 裁掉 | 范围裁剪决定 |
| `HOLD` | 拿不准,挂起待盲标数据交叉印证 | 盲标回收后二审 |

> 纪律:每项 5–10 分钟,只定性到码,不写终审论证。超过 10 分钟仍犹豫 → 打 `HOLD` 走人。`HOLD` 超过抽样量 20% 说明处置码定义有歧义,停下来修定义再继续。

## 逐桶审查程序

### B1 无可选轨迹(24 项)

核心问题:**"无可选"是诚实的还是怯懦的?**

1. 先只读证据区左半(facts + narrative + rules + 各候选 trajectory_summary),**遮住 system_verdicts 列**,自己对每条候选给一个直觉 verdict;
2. 再对照系统 verdicts:
   - 你也全判不了 → 看缺什么:相位缺失 → 大概率 `FEAT-GAP` 或 `CORRECT-ABSTAIN`(区分标准:缺的信息数据里有没有——有但没进摘要是 FEAT-GAP,数据里就没有是 CORRECT-ABSTAIN);
   - 你能 clear 某条而系统 uncertain → 记下差异点(你用了哪个特征字段),`JUDGE-MISS`;
   - 系统 verdicts 与 facts 矛盾(如 facts 说无行人却按行人规则 veto)→ 回查 SceneFacts 原始来源,`FACT-FIX`。
3. evidence_note 写「你的判断 vs 系统判断 + 差异归因」一句话。

### B2 exclude-chosen(20 项)

核心问题:**precheck 踢掉这条 GT 是对的吗?**

1. 看被排除 GT 的 trajectory_summary + 触发的 precheck 谓词 + 阈值;
2. 三分支:
   - GT 确实明显违规(如真实司机闯了黄灯)→ precheck 对,但 exclude 导致场景不可评分是**计分口径问题**:该场景其余候选仍可评 → `BENCH-FIX`(action 写「exclude 仅剔除该候选而非整场景」);
   - GT 是临界行为被过严阈值误伤(缓慢滚动、压线停车)→ `BENCH-FIX`(action 写「谓词 X 阈值放宽/改人工」),`needs_blind_confirmation=true`;
   - precheck 依据的事实本身错 → `FACT-FIX`。
3. 顺手记录:模型偏好被排除 GT 这件事,在该场景下你认为是合理偏好吗(是/否/不确定)——这一列汇总后是「模型偏好人类轨迹」现象的定性证据。

### B3 uncertain 候选(30 项)

核心问题:**uncertain 的直接成因是哪一环?**

按 decided_by 分两条路径:

- `rule_engine` 给的 uncertain:对照规则引擎的判定条件,回答「该候选落入哪个设计上的困难区间(creeping/临界停车/提前起步)」——落入 → 符合设计,再看 LLM 兜底为何没接住(超时降级?也判 uncertain?)→ 分别 `JUDGE-MISS` / 按降级原因记;未落入任何设计区间却 uncertain → 引擎条件覆盖缺口,`JUDGE-MISS`(note 标注「rule_engine gap」)。
- `llm` 给的 uncertain:读 LLM 的 reason 文本,归类其自述理由:引用信息缺失(→ 与 facts 核对,真缺 = `FEAT-GAP`/`CORRECT-ABSTAIN`,不缺 = `JUDGE-MISS`);引用规则冲突(→ 查 overrides 是否正确传达,`FACT-FIX`/`BENCH-FIX`);理由含糊无实质 → `JUDGE-MISS`(note 标「prompt」)。

### B5 scene-0286(1 项,单独出裁定记录)

按四选一框架逐步排除,固定记录格式:

```
scene_id / frame_token:
触发条件:C-RED-PHASE + C-EMERGENCY-ACTIVE
override 链:R-YLD-04 OVERRIDES R-SIG-01
步骤1 事实核查:emergency 车辆 annotation 是否存在/moving/attribute 支持执行任务?
  → 否 ⇒ 裁定 FACT-FIX,结束
步骤2 被选轨迹行为:越线是否伴随对特种车辆的让行几何(减速/避让)?
  → 是 ⇒ 裁定 BENCH-FIX(benchmark 未过 ConflictResolver),最可能
  → 否 ⇒ 步骤3
步骤3 override 语义:R-YLD-04 是否本不该在此几何关系下豁免红灯约束?
  → 是 ⇒ override 设计问题(BENCH-FIX 变体,action 写 override 条件收紧)
  → 否 ⇒ 裁定 JUDGE-MISS(模型真错)
四选一结论 + 证据引用(annotation token / 特征字段值)+ v1 结果不改动声明
```

## 汇总与报告

全部裁定完成后,脚本(或手动)聚合出:

1. **处置码分布**(总体 + 分桶),用抽样比例外推给出三个区间估计:246 个不可评分中「benchmark 缺陷(可修)/ 数据固有限制 / 系统缺陷」的大致占比——报告里明确写这是抽样外推,非全量核查;
2. **benchmark v2 修订清单**:所有 `BENCH-FIX` 项的 action 去重合并,每条附支持它的 audit_item_id 列表(证据链);
3. **HOLD 清单**:待盲标回收后二审的项;
4. 一页诊断报告:三个占比 + 修订清单 + scene-0286 裁定 + 对 uncertain 主因的一句话结论(对照 SRS 已知风险点,说明是否走信号灯退路)。

## 与其他工作的衔接

- 诊断审计的 `BENCH-FIX` 清单 → benchmark v2 实现 → 2×2 正式消融跑在修订后口径上;
- `needs_blind_confirmation` 与 `HOLD` 项 → 盲标数据回收后,在样本重叠处交叉印证,写入报告附注;
- `SCOPE-CUT` 结论(尤其 emergency)→ 同步更新 Layer 2 规则图(按 spec 的 W1 裁剪规则删 C-EMERGENCY-ACTIVE / R-YLD-04)与论文范围声明。
